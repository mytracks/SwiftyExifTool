# Design

## Context

The repository has no code yet. This change creates the package and the
reading core that all later roadmap entries build on: CR3 and RAF (entries 5
and 6) will hand embedded TIFF blocks to the same parser, the Inspector
(entry 2) will display the result model, the JSON export (entry 3) will
serialise it, and writing (entry 8) needs the lossless stored values and value
locations. See proposal.md for scope; the specs define the behaviour.

Constraints that shape the design: Foundation only, no ImageIO; iOS
sandboxing; RAW files of tens of MB; Swift 6 strict concurrency; and the
clean-room policy, under which every tag name and conversion must be sourced
from a published specification or a black-box exiftool observation.

## Goals / Non-Goals

**Goals:**
- A parser that is safe on hostile input by construction, not by testing
  alone.
- A result model that later changes can extend (new groups, new value
  sources) without breaking callers.
- A fixture and snapshot workflow that makes provenance and exiftool parity
  checkable by `swift test`, without exiftool installed.

**Non-Goals:**
- Performance tuning beyond avoiding whole-file reads. No benchmarks in this
  change.
- A general JSON export or a comparison runner for real RAW files (entry 3).
  The snapshot comparison here is test-only.
- Public extensibility of tag tables by callers.

## Decisions

### D1. Package layout

```
Package.swift                      swift-tools-version 6.0, macOS 14 / iOS 17
Sources/SwiftyExifTool/            library product
  IO/          byte sources, bounds-checked binary reader
  Detection/   signature detection
  TIFF/        header, IFD walker, field decoding, limits
  Tags/        tag tables, value and display conversions, provenance
  Model/       public result types, errors, warnings
Sources/FixtureKit/                internal target: TIFF builder + fixture catalogue
Sources/fixtures/                  executable (macOS only, dev tool)
Tests/SwiftyExifToolTests/
  Fixtures/synthetic/*.tif         generated, committed
  Snapshots/exiftool-13.55/*.json  recorded, committed
  Snapshots/deviations.json        documented deviations
```

Only `SwiftyExifTool` is a product, so consumers never build `FixtureKit` or
the tool. *Alternative:* fixtures built in memory at test time only. Rejected:
snapshots must refer to exact bytes on disk that exiftool has seen; committing
the files and checking them against the regenerated bytes keeps both in step.

### D2. Byte sources instead of whole-file `Data`

An internal protocol `ByteSource` offers `size` and
`read(offset:count:) throws -> Data`. Two implementations:

- `DataByteSource` for in-memory input.
- `FileByteSource` on `FileHandle` (read-only), with a small cache of aligned
  64 KiB pages so the many tiny IFD reads do not each cost a system call.
  Opened and closed inside one read call.

*Alternative:* `Data(contentsOf:options: .alwaysMapped)`. Rejected: a file that
shrinks or disappears while mapped (external volumes, iCloud, other
processes) raises SIGBUS instead of a catchable error, and mapped pages
still count against the memory limits of iOS apps. With FileHandle the bytes
read are exactly the ranges the structure points to, which also makes the
bounded-reading requirement testable with a counting source.

### D3. Bounds-checked reading

All file access goes through a `BinaryReader` value (source, base offset,
byte order). Every read takes an absolute offset and length, checks
`offset + length <= size` with overflow-checked arithmetic, and throws an
internal out-of-bounds error that the walker turns into a warning. No raw
pointers, no unchecked subscripts, no force unwraps on file data.

Before decoding a value the walker computes `count × typeSize` with
`multipliedReportingOverflow` and compares it with the remaining file size.
Memory is therefore allocated in proportion to bytes that actually exist,
never to declared counts.

Offsets inside TIFF data are relative to the TIFF header. The parser takes a
`baseOffset` (0 for TIFF files) and reports absolute file offsets, so CR3 and
RAF can reuse it for embedded TIFF blocks.

### D4. Directory walking and limits

The walker visits directories depth-first: entries in stored order, a
sub-directory's tags inserted at its pointer's position, then the next IFD of
the chain (observed order, see Sources). Recursion depth is capped, so
recursion is safe; a set of visited absolute offsets prevents cycles.

Limits live in a public `ReadingLimits` struct with documented defaults,
passed optionally to the read call:

| Limit | Default | Reason |
|---|---|---|
| directories per file | 256 | RAW files have well under 20 |
| nesting depth | 8 | IFD0 → ExifIFD → InteropIFD is 3; MakerNotes add 1–2 later |
| loaded value size | 64 KiB | larger values (previews, strips, blobs) are reported with location only |

A directory whose entry table does not fit is skipped as a whole, matching
exiftool's observed behaviour. A bad entry inside a valid table is skipped
on its own.

### D5. Result model

```swift
public struct Metadata: Sendable, Hashable {
    public let fileType: FileType          // .tiff for now
    public let byteOrder: ByteOrder?
    public let tags: [Tag]                 // traversal order
    public let directories: [Directory]
    public let warnings: [ReadWarning]
    public func tag(_ group: TagGroup, _ name: String) -> Tag?
    public func tags(named name: String) -> [Tag]
}

public struct Tag: Sendable, Hashable {
    public let group: TagGroup             // "IFD0", "ExifIFD", "File", …
    public let name: String
    public let id: UInt16?                 // nil for File group tags
    public let isUnknown: Bool
    public let stored: StoredValue?        // nil for File group tags
    public let value: TagValue             // equals exiftool -n
    public let displayText: String         // equals exiftool default output
    public let location: ValueLocation?    // entry offset, value offset, length
}

public enum TagValue: Sendable, Hashable {
    case integer(Int64), double(Double), string(String), binary(length: Int)
}
```

`StoredValue` holds the field type, the count and the decoded contents
(`[UInt32]`, `[Int32]`, rationals as numerator/denominator pairs, floats,
bytes, or `.notLoaded` above the size limit). It is lossless so that writing
(entry 8) can work from it. `TagGroup` is a string-backed struct rather than
an enum so later changes add groups (`XMP-dc`, `Canon`, …) without breaking
callers' exhaustive switches.

`TagValue` mirrors what `exiftool -n` prints: integers, decimals, strings, or
a binary placeholder. Arrays are strings joined by spaces, as observed
(`2 3 0 0`). *Alternative:* expose only exiftool-style strings. Rejected: it
loses precision and types that writing and callers need. *Alternative:* only
typed values. Rejected: parity with exiftool output is the project's
compatibility target, so both renderings must be first-class.

Reading uses Swift typed throws:
`MetadataReader.read(contentsOf: URL, limits:) throws(ReadError) -> Metadata`
and `read(data:limits:)`. `ReadError` has the cases `fileAccess(underlying:)`,
`unsupportedFormat(DetectedFormat)` and `unknownFormat`. All functions are
synchronous and non-isolated; callers choose their own task or queue. The
reader holds no shared mutable state, and the tag tables are immutable
`static let` values, so concurrent reads are safe.

### D6. Tag tables and conversions

Each definition is a value: ID, name, table (`main` or `gps`), value
conversion, display conversion, and provenance. Display conversions are a
closed set of cases (`.none`, `.enumeration([Int64: String])`,
`.bitField`, and a few named formatters such as fractional exposure time,
GPS coordinate or version string) instead of arbitrary closures, so tests can
enumerate them. Values not covered by an enumeration render as
`Unknown (<value>)`.

Provenance is a value too: `.specification(document, section)` for the
definition itself, and the name and display text are additionally confirmed
by the fixture snapshots. A test checks that every definition has a
specification source and appears in at least one snapshot, or is listed as
hidden by exiftool (the embedded blocks, see the exif-tags spec).

Lookup is a dictionary per table, built once from the definition list.

### D7. Fixtures and snapshots

`FixtureKit` contains a small `TIFFBuilder` (byte order, IFDs, entries of
any field type, raw byte patches for malformed cases) and a catalogue of
named fixtures written in Swift. The `fixtures` tool has two commands:

- `swift run fixtures generate` writes every catalogued fixture to
  `Tests/SwiftyExifToolTests/Fixtures/synthetic/`.
- `swift run fixtures snapshot` runs, per fixture, the installed exiftool with
  `-j -a -G1 -u -n`, `-j -a -G1 -u` and `-v2`, drops the `System` and
  `ExifTool` groups (keeping warnings), and writes one JSON file per fixture
  together with the exiftool version and the exact commands.

A test regenerates every fixture in memory and compares it with the committed
file, so the catalogue and the committed bytes cannot drift. The conformance
test reads each fixture with the library and compares groups, names, values
(numbers within a relative tolerance of 1e-9, everything else exactly) and
display texts with the snapshot. `deviations.json` lists accepted
differences, each with a reason and the spec requirement that sanctions it.

To cover many values of one enumerated tag in a single fixture, the
catalogue puts one value per chained IFD (IFD0, IFD1, …), relying on the
shared main table (exif-tags spec). GPS values need one fixture per value.

**Observation rule.** Fixtures may only contain tag IDs taken from published
specifications or from later changes' sourced definitions. Filling fixtures
with every possible tag ID to harvest names would amount to dumping
exiftool's tag database, which docs/clean-room.md forbids. This rule is
added to docs/clean-room.md in this change.

### D8. Fuzzing

A seeded random generator (deterministic, no dependency) produces files from
a valid header plus random bytes, and mutations of every committed fixture
(bit flips, truncations, offset overwrites). The test runs a fixed number of
iterations under `swift test`, with a larger count selectable by an
environment variable for local runs. A failure prints the seed and iteration.

## Sources

Specifications:
- TIFF Revision 6.0 (Adobe, 1992): header, IFD layout, field types, baseline
  and extension tags.
- Adobe PageMaker 6.0 TIFF Technical Notes (draft, 14 September 1995),
  TIFF Tech Note 1 "TIFF Trees": SubIFDs tag 0x014A.
- CIPA DC-008-2026 (Exif 3.1): 0th IFD, Exif, GPS and Interoperability tags,
  the UTF-8 field type. Exif 3.1 defines only InteroperabilityIndex in the
  Interoperability IFD; InteropVersion (0x0002) stays unknown until a source
  is available.
- XMP Specification Part 3 (Adobe), Table 12: tags 700 (XMP) and 33723 (IPTC).
- ICC Technical Note "Embedding ICC profiles", Table 2: tag 34675 (ICC profile).
- BigTIFF design (TIFF version 43): signature only.
- ITU-T T.81 (JPEG SOI marker), PNG specification (ISO/IEC 15948 signature),
  ISO/IEC 14496-12 (`ftyp` box): signatures only.

Black-box observations, exiftool 13.55, on synthetic fixtures built during
planning (to be re-recorded as committed snapshots):
- groups `IFD0`, `IFD1`, `IFD2`, `SubIFD`, `SubIFD1`, `ExifIFD`, `GPS`,
  `InteropIFD`, and the traversal order;
- names ImageHeight (0x0101), ISO (0x8827), InteropIndex, InteropVersion,
  ApplicationNotes (0x02BC, via `-v2`), and the shared main table;
- unknown-tag names `Exif_0x…` and `GPS_0x…` with `-u`;
- values and display texts: ExposureTime `0.004` / `1/250`, Orientation `6` /
  `Rotate 90 CW` and `Unknown (99)`, Flash `16` / `Off, Did not fire`,
  GPSVersionID `2 3 0 0` / `2.3.0.0`, GPSLatitudeRef `North`, ResolutionUnit
  `inches`, ExifByteOrder `II`/`MM` with both display texts, FileType,
  FileTypeExtension and MIMEType;
- trailing spaces and NULs stripped; non-UTF-8 bytes shown as `?`;
- warnings "Bad IFD0 directory" and "Bad ExifIFD directory"; a self-linked
  IFD0 read a second time as IFD1; XMP and MakerNote blocks hidden from JSON.

## Risks / Trade-offs

- [Display formatting has many small rules (rounding, signs, units) learned
  only by observation] → one fixture per conversion case, exact string
  comparison, and a deviations list instead of silent mismatches.
- [Snapshots tie tests to exiftool 13.55] → the version is stored with every
  snapshot; re-recording with a newer exiftool is a deliberate, reviewable
  diff.
- [Tag tables in Swift are long and slow down compile times] → plain array
  literals of simple values without type inference cost; revisit if builds
  become slow.
- [A 64 KiB page cache can read slightly beyond what the structure needs] →
  the bounded-reading test measures pages read, and the limit in the spec
  (under 1 MB for a 200 MB file) leaves ample room.
- [Typed throws and public enums: adding a `ReadError` or `FileType` case
  later breaks callers that switch exhaustively] → acceptable while the
  package is pre-1.0; the documentation tells callers to keep a `default`
  branch, and new cases are called out in each change's proposal.
